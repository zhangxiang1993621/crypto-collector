## 1. P0 — 立即修复（数据丢失 / 静默全面失败 / 崩溃）

### P0-1 [Critical] 面板一键触发 `clean_all --yes`，无确认清空核心业务表
- 位置：`task_manager/scheduler_engine.py:168-177`、`task_manager/gui.py:318-326`、`gui.py:264-289`、`tools/clean_all.py:19-28`
- 证据：内置任务命令为 `python tools/clean_all.py --yes`；`_run_now()` 直接 `self.scheduler.run_now(name)`，无任何对话框；"执行分类全部"只有一句泛化 `askyesno`（`gui.py:285`），不区分破坏性任务。
- 影响：单击一次即删除 `post_tags/likes/bookmarks/comments/posts`，直接命中生产 Supabase。
- 建议：GUI 对破坏性任务强制二次确认（键入 `DELETE`）；把 `clean_all` 移出内置任务；去掉内置的 `--yes`。

### P0-2 [Critical] `clean_all` 的"孤儿标签"清理实际会删除**全部** tags
- 位置：`tools/clean_all.py:19-28`（顺序）、`:56-68`（SQL）
- 证据：`DELETE_ORDER` 先清空 `post_tags`，随后 `DELETE FROM tags WHERE id NOT IN (SELECT tag_id FROM post_tags ...)`；此时子查询为空集，`NOT IN (空集)` 恒真 → 删除全部 tags。而预统计是在 `post_tags` 尚存时算的，展示数字与实际不符；返回行数又因 P1-2 恒为 0。
- 影响：与 P0-1 叠加，一次点击 = 清空帖子 **和** 全部标签。
- 建议：若需保留被引用标签，把孤儿清理移到清空 `post_tags` **之前**；否则明确改为"清空全部标签"并如实统计 rowcount。

### P0-3 [Critical] CI 永远为绿：27/27 job 吞掉失败
- 位置：`.github/workflows/scheduler.yml`（`continue-on-error: true` × 27；`|| echo` × 32）
- 证据：`:34 continue-on-error: true`、`:47 run: python crypto/price_collector.py || echo "[FAIL]"`，其余 job 同构；`if:` 0 次。
- 影响：脚本 100% 失败（连不上库、解析报错）时 workflow 仍成功；且 job 级 `continue-on-error` 不阻止"安装步失败 → 后续 `Run` 被 `if: success()` 跳过"，采集根本没跑而 run 仍绿。失败标记还不统一（`[FAIL]`、`CloakBrowser blocked`、`... done` 等），无法统一检索。
- 建议：删除 job 级 `continue-on-error` 与 `|| echo`；确需容忍失败的少数 job 用 step 级；末尾加汇总步，发现统一失败标记即 `exit 1`。

### P0-4 [Critical] esports 详情页异常 → `UnboundLocalError` → 整轮 0 入库
- 位置：`esports/esports_scraper.py:145-190`（`tags` 赋值在 `:161` 的 try 内；`:184-186` 的 except 只重置 `content`；`:189` 读 `tags`）
- 影响：`page.goto`/`wait_for_selector` 超时（`:149/:151`）即抛 `UnboundLocalError`，异常不在任何 try 内，直接冲出 `run()`，整个 esports 任务失败。网络抖动即可复现。
- 建议：函数开头 `tags: list[str] = []`；per-article try/except，单条失败只跳过。

### P0-5 [Critical] 7 个脚本入库前无数据库查重 → 每次调度重复发帖
- 位置：`news_scrapers/tribunbola/tribunbola_scraper.py:251`、`ibl_data/ibl_data_scraper.py:387,407`、`sport_detik/detik_scraper.py:284`、`bolasport/bolasport_scraper.py:305`、`indo_news/indo_news_scraper.py:432`、`dailysports/dailysports_scraper.py:278`、`mainbasket/mainbasket_scraper.py:271`
- 证据：这些文件只有内存内 `deduplicate()`（按 title[:80]），grep 不到任何 `SELECT ... FROM posts`；对照 pintu/indodax/bitget/okx/osl/mobee/tokocrypto 有 `filter_new_only()`。`ibl_data` 更直接使用硬编码标题 `"🏀 Klasemen IBL Gopay 2026"`，**每天都必然新增同名帖**。
- 建议：统一按 `(category_id, title)` 查重，或给 `posts` 加唯一约束 + `ON CONFLICT`。

### P0-6 [Critical] `goal_scraper` 用含实时比分的标题去重，`match_id` 参数被忽略
- 位置：`sport/goal/goal_scraper.py:344-363`、`389-425`、`505-506`
- 证据：标题内嵌状态与比分（如 `... {a} 1-0 {b} (Sedang Berlangsung)`）；`upsert_post(title, content, author_id, category_id, match_id)` 的函数体从未引用 `match_id`，去重仅 `select_one("posts", {"title": title})`。
- 影响：`scheduler.yml:252` 每天跑 `--save --live`；一场比赛 LIVE 期间每次比分变化、以及 LIVE→FT 都会生成新标题 → 每次都走 insert，同一场比赛刷出多篇帖子。
- 建议：以 `match_id` 为稳定业务键去重（或标题不含比分，比分只更新 content）。

## 2. P1 — 尽快修复（正确性 / 安全 / 可靠性）

### P1-1 [High] binance 调用未导入的 `update_one`

### P1-2 [High] `db_direct.update_one` 恒返回 0
- 位置：`db_direct.py:407-408`（配合 `:135-137`）；连带 `tools/cleanup_tags.py:14-19`、`tools/clean_all.py:56-68`
- 影响：21 处调用无法区分更新成功/条件不匹配；运维脚本的"已修复/已删除 N 行"全部谎报为 0。
- 建议：`execute_sql` 在 `fetch=False` 时返回 `cur.rowcount`，或直接在 `update_one` 内读取 rowcount。

### P1-3 [High] VACUUM 语句语法错误
- 位置：`db_direct.py:154-158`（`VACUUM FULL (VERBOSE, ANALYZE) "schema"."table"`，且 `full` 默认 `True`）、`tools/vacuum_db.py:100-101`
- 依据：PostgreSQL 语法为 `VACUUM [ ( option [, ...] ) ] [ table ]`，`FULL` 必须放在括号内 → `VACUUM FULL (VERBOSE, ANALYZE) t` 报语法错误（本机未执行，依据官方语法）。
- 影响：`vacuum_table()` 默认路径必抛异常；`vacuum_db.py --full` 只打一行 error 后继续，运维误以为已回收。
- 建议：`VACUUM (FULL, VERBOSE, ANALYZE) ...` / `VACUUM (VERBOSE, ANALYZE) ...`。

### P1-4 [High] 本地面板超时形同虚设 + 超时不回收子进程
- 位置：`task_manager/scheduler_engine.py:314-326`
- 证据：`for line in process.stdout:` 阻塞到 EOF 才轮到 `process.wait(timeout=600)`；`TimeoutExpired` 分支无 `kill()`。
- 影响：挂起且无输出的任务永久占死线程（`max_instances=1` 后该任务不再触发），多任务卡死耗尽线程池；文档 `docs/scheduling.md` 承诺的"10 分钟超时"不成立。
- 建议：看门狗/读线程 + 截止时间，超时与异常路径统一 `kill()` 进程树。

### P1-5 [High] 任务失败被面板记录为"成功"
- 位置：`task_manager/scheduler_engine.py:236-239`（判定）与 `:280-328`（吞异常、非零退出只 return）
- 影响：APScheduler 只会发 `EVENT_JOB_EXECUTED`，`event.exception` 恒 `None`，"结果"列恒为"成功"，叠加 CI 的 `|| echo` 后失败完全不可见。
- 建议：非零退出或异常时 `raise`，让 listener 收到 `EVENT_JOB_ERROR`。

### P1-6 [High] 23 条相同 cron × 27 个无守卫 job
- 位置：`.github/workflows/scheduler.yml:5-27`；根因 `task_manager/scheduler_engine.py:74-75`（按位置取 cron）、`:201-204`（回写 `on.schedule`，且不过滤 `enabled`）
- 影响：GitHub 的 `schedule` 每条都是独立触发器、每次触发运行全部 job；**是否对完全相同 cron 去重 GitHub 未作承诺（未验证）**。无论去重与否都不符合预期：要么整套 workflow 一天被触发约 23 次、25+ job 同分钟并发重写同一库，要么 22 条计划静默失效。各 job 原本的差异化节奏已丢失。
- 建议：合并为一条 `0 0 * * *`（或每 job 独立 workflow），需要区分频率时用 `if: github.event.schedule == '<cron>'`；`sync_to_yaml` 改为按 job name 关联而非下标。

### P1-7 [High] 6 个交易所 job 未传分类变量，CI 落到 `Hot Tokens`
- 位置：`scheduler.yml:84-88, 98-101, 125-128, 264-266, 279-281, 294-296`；脚本 `tokocrypto_scraper.py:52`、`indodax_scraper.py:55`、`mobee_scraper.py:32`、`osl_scraper.py:30`、`bitget_scraper.py:29`、`okx_scraper.py:29`

## 4. 未发现明显问题的方面（优点）

- **SQL 值参数化到位**：`db_direct` 所有数据值均走 `%s`，未发现值级注入；SQLite 侧全部 `?` 参数化。
- **事务边界正确**：`batch_upsert`/`insert_many` 用 `autocommit=False` + 显式 `commit/rollback`。
- **连接无泄漏**：游标/连接都在 `finally` 关闭；Telegram `get_conn()` 每次新建关闭，未违反 `check_same_thread`。
- **`sys.path` 处理正确**：40 个脚本均含 `sys.path.insert(..., Path(__file__).parent...)`，`from db_direct import` 不会因 cwd 失败。
- **部分去重方向正确**：pintu/indodax/bitget/okx/osl/mobee/tokocrypto 有 `filter_new_only`；fastscore 用固定标题按 title upsert；fifa_blog/binance/esports 有 `existing_titles`。
- **无危险动态执行**：未见 `eval`/`exec`/`os.system`；唯一 `subprocess` 在本地调度器（P1-8 已述）。
- **无裸 `except:`**（全项目 0 处），异常至少记录日志（个别 `except Exception: pass` 除外，见 P1-1/P1-15）。
- **密钥未入库**：`.env` 从未被 commit；`.gitignore` 覆盖 `.env`（任意层级）、`*.session`、`*.db`、`task_config.json`；workflow 全走 `secrets.*`/`vars.*`。
- **`create_bots.py`** 对 service_role key 的使用属合理 Admin API 用途，未打印/回传密钥。
- **CloakBrowser 浏览器对象**在 `finally` 中 `close()`（`us_stock_scraper.py:571-582`），仅 `new_page()` 自身失败会轻微泄漏。
